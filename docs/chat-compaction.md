# 会话上下文自动整理

主聊天入口（Web、企微、HTTP API、MCP）支持在回答交付后自动整理上下文。默认关闭，关闭时沿用包含当前问题的五轮窗口。独立的知识同步、固件匹配等任务不使用此策略。

## 启用

在真实部署的 `.env` 中显式设置，重新构建并重启主 Agent：

```ini
CHAT_COMPACTION_ENABLED=true
CHAT_COMPACTION_TRIGGER_TOKENS=384000
CHAT_COMPACTION_KEEP_RECENT_ROUNDS=5
```

`CONTEXT_WINDOW` 仍为模型的实际容量；启用时必须满足 `触发阈值 < CONTEXT_WINDOW - MAX_TOKENS - 16384`。例如现有的一百万 token 配置可以使用上述阈值。环境配置只在服务启动时加载，没有修改配置的公开接口。只需更新主服务，Bridge、模型服务及隧道无需调整。

## 行为

- 原文持续累积。每次回答完成、指标保存和响应结束（机器 API 为任务结果落盘）后，使用最近有效 usage 检查阈值，包括缓存及输出；缺少 usage 时结合消息和注入内容估算。
- 达到阈值后，完整保留最后五条用户消息及它们各自的回答、工具调用和返回。更早的新原文与上一份摘要交给同一聊天模型总结，不拆分轮次。摘要使用 Pi 原生总结流程和 compaction 记录，输出最多 8192 token。
- 摘要请求不加载聊天业务系统提示、记忆或工具；摘要作为历史资料使用，不能改变工具权限。
- 整理使用独立的单并发队列。同会话新问题先接收并等待整理完成，Web/企微显示“正在整理上下文，完成后继续回答”；普通问答的全局并发名额不会被整理或该等待占用。
- 两分钟总超时，临时错误允许重试一次。失败保留全部现有上下文及已交付回答，至少一分钟后才重新尝试。没有旧原文可总结时跳过，即使最近五轮本身很大也不截断。接近模型容量时返回明确提示。
- 正在整理时删除或重命名会话、修改 Agent 设置以及关闭服务，都会先协调取消整理；失败或取消不能写入半份摘要。

## 旧会话与记录

首次启用并打开旧会话时，在原 SDK JSONL 中记录上下文起点，从当时最后五轮开始累积；更早历史不自动读回或集中总结。起点与 compaction 检查点在重启后保留。关闭开关会恢复五轮推理策略，不删除已保存记录。

原始用户、回答和工具消息继续保存在 JSONL，历史分页、附件、工具详情和 `/patrick_detail` 从原始分支记录读取。五轮边界以用户消息条目 ID 为准，摘要不计为用户的一轮，历史轮次不会重编号。30 天会话保留策略不变。

摘要、上下文起点和锁按既有会话及数据目录隔离。群聊维持现有共享会话边界，没有新增群内个人隔离。

摘要调用单独记入 `.data/usage-ledger/`，来源为 `chat-compaction`，不计入上一轮问题的请求数、耗时和 token。Agent 日志记录会话 ID、整理前 token、耗时和成功/失败，不输出摘要正文或凭据。

压缩后的首次新请求尚无新 usage 时，不复用压缩前的大上下文 usage，避免重启或连续检查导致重复总结。
